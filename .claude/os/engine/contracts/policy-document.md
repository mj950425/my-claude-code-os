# 정책 문서 표준

정책 문서는 작업 설정에 선언된 속성 하나 이상을 설명한다. 문서와 에이전트 전달 정책은 정책 페이지에 보이며, 여러 속성 문서에서는 공통 규칙과 각 속성 규칙을 구분한다.

## 문서 형식

v2 정책 페이지에는 사람이 읽을 정책 전체를 표시한다. 문서는 속성별 도메인 표현만 담고, 특정 판독기나 속성 이름을 가정하지 않는다. 목적은 무엇을 분류하는지, 허용값은 이름과 뜻, 규칙은 사람이 적용할 판단 기준을 설명한다. 응답 코드와 실행 설정 같은 기계 값은 프로필에 둔다.

```markdown
# 상품 분류 정책

## 목적
의류 상품의 대상 고객 성별을 분류한다.

## 허용값
- 남성 — 남성을 대상으로 분류한 상품.
- 여성 — 여성을 대상으로 분류한 상품.

## 규칙
### G1 · 근거 확인
- 내용: 확인할 수 있는 정보만 근거로 사용한다.
- 우선순위: 공통
- 판례: 없음

### P1 · 직접 문구
- 내용: 대상 상품을 직접 설명하는 성별 문구에 따라 판정한다.
- 우선순위: 1
- 판례: 없음
```

여러 속성을 설명할 때는 `## 목적` 뒤에 속성 표시 이름으로 `##` 절을 하나씩 둔다. 각 속성 절에는 선택적으로 자연어 설명을 두고, `### 허용값`과 `### 규칙`을 차례로 작성한다. 서로 다른 속성을 함께 제한하는 기준은 `## 공통 규칙`에 쓴다. 공통 규칙은 `### ID · 제목`으로 시작하고 같은 내용·우선순위·판례 속성을 사용한다.

규칙 ID는 판정 결과와 판례에서 참조할 식별자다. 제목·내용·우선순위·판례를 관리한다. v2 문서에는 각 규칙에 이 세 항목만 둘 수 있으며, 설명이나 응답 코드 표를 문서 바깥에 덧붙이지 않는다.
공통 규칙은 모든 판정에 적용하며 공통 규칙 절의 우선순위는 `공통`으로 쓴다. 숫자 우선순위는 각 속성 안에서 작은 수부터 적용하며 중복할 수 없다. 규칙 ID는 문서 전체에서 고유해야 한다. 같은 이름의 정책 절도 중복할 수 없다.
허용값의 이름과 설명은 문서에 둔다. 허용값 코드는 `profile.json`의 `policyTask.fields[].valueCodes`로 연결한다.

## 작업 설정

`policyTask.documentFormat`은 `policy-document-v2`다. `policyTask.definitions`는 정책 문서 경로다.
`policyTask.fields`에는 `id`(내부 속성 코드), `name`(표시명), `valueCodes`(문서의 값 이름 → 응답 코드)를 선언한다.
v2는 여러 속성을 한 문서에 연결할 수 있다. 속성 표시 이름은 프로필의 `fields[].name`과 정확히 맞아야 한다. 기존의 단일 속성 v2 문서도 계속 읽는다.

## 전달, 외부 동기화, 판례

`policy_document.load_document`가 v2 문서 구조와 작업 설정의 연결을 읽고 잘못된 문서나 연결은 거절한다. 과거 형식은 기존 판독 어댑터에서 계속 읽는다.
SDK와 정책 페이지는 `policy_prompt.render_agent_policy`가 만든 같은 목적·규칙·허용값을 사용한다. GT task의 판독 경로도 이 렌더러를 부르므로 SDK가 정책을 전달하는 데 `promptDelivery`는 필요하지 않다. 실제 호출은 [`gt_task.reader_policy`](../scripts/gt_task.py)와 [`gt_review_render`](../scripts/gt_review_render.py)의 공유 렌더 경로를 따른다.

`policyTask.promptDelivery`는 **외부 운영 프롬프트 파일과 어댑터의 버전/해시 선언을 동기화하는 선택 설정**이다. 외부 리소스의 삽입 지점과 어댑터 버전 선언을 함께 갱신해야 할 때만 선언한다. SDK가 실행 중 `definitions`를 읽는 동적 전달과 별개다. 기존 관찰·계산표는 v2 정책 문서에 포함하지 않는다.

규칙의 `판례`는 그 규칙을 설명하도록 승인해 연결한 결정/사례의 식별자나 링크다. `판례: 없음`은 이 규칙에 승인되어 명시적으로 연결된 선례가 없다는 유효한 상태이지, 사람이 확정한 GT 답이나 정책 질문이 하나도 없다는 뜻은 아니다.

두 기록을 구분한다. 정책 경계 질문의 `OPEN`은 아직 답이 없는 질문이며, 그 상태만으로 확정 사례 후보나 판독 규칙이 되지 않는다. 반면 SDK의 일반 사례 검색은 GT 검수 원장에서 사람이 `CORRECT` 또는 `CONFIRM`으로 답한 질문을 같은 프로필·필드 안에서 후보로 모으고, 현재 사례 키를 제외한다. 규칙의 `판례`에 그 `GTD-*`가 연결돼 있을 때 후보는 해당 규칙 ID도 가진다. 연결되지 않은 후보에는 특정 규칙을 가장하지 않는다. 원장이나 열린 질문 파일을 검색 결과가 수정하지 않으며, 가상의 판례 ID를 만들지 않는다.

정책 페이지는 읽기/표시 결과다. 사람이 편집하는 정본은 `policyTask.definitions`가 가리키는 파일이다.
이전 실험의 저장된 정책과 결과는 당시의 기록으로 유지한다.

## 사람이 직접 등록하는 증분 판례

증분 검수에서 값을 확정한 뒤 `판례 등록`을 누르고 판단 근거를 적으면 명시적 판례로 등록한다. AI 질문이나 두 번째 검수자는 필요하지 않다. 선택적으로 현재 정책의 규칙 ID를 연결한다.
`POST /incr-precedent`는 현재 판정 ID를 대조하고, 허용값 밖·보류·미해결 의견 차이가 있는 판정을 거부한다. 등록은 `.claude/incr/<task>/precedents.jsonl`에 출처 판정 ID·근거·규칙 ID·등록자·시각·정책 해시와 함께 추가한다. 기존 판정 원장은 변경하지 않는다.
판례 검색과 정책 문답은 같은 활성 목록을 읽는다. 상품 판정이 교체되면 이전 판정에 연결된 판례는 검색에서 제외된다. 등록 근거를 수정하면 같은 판례 ID의 새 기록을 추가한다. 현재 판독 상품 자체의 판례는 자기 정답 누출을 막기 위해 제외한다.
