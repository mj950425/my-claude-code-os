# 정책 준비도 검수

사용자가 새로운 판정 기준을 만들거나 기존 규칙을 고치라고 하면 이 절차를 따른다.

## 준비

1. 과제의 입력 단위, 판정 대상, 허용값을 사용자 자료에서 찾는다. 모르는 사실이나 사례를 지어내지 않는다.
2. `.claude/os/attributes/<id>/definitions.md`에 허용값과 `### 판정 규칙`을 작성한다. 규칙마다 고정 ID, 제목, 자연어 `내용`, 서로 겹치지 않는 양의 정수 `우선순위`, 추적 가능한 `출처`를 적는다. 판례는 실제 연결할 사례가 있을 때만 기록한다.
3. 운영 프롬프트가 이미 있으면 `profile.json`의 `policyTask.promptDelivery`에 리소스, 어댑터, 표식, 해시·버전 `adapterTargets`를 적는다. 아직 운영 연결이 없으면 GT 없는 최소 `policyTask`를 선언한다. GT 파일은 필수가 아니다.

## 독립 검수

`policy-readiness-review.js`를 실행해 `policy-contract-reviewer`, `policy-counterexample-reviewer`, `policy-prompt-reviewer` 결과를 받는다. 입력에는 과제명, 절대 경로가 아닌 프로젝트 기준 정의 파일 경로, 허용값, 생성된 추론 프롬프트와 블라인드 검수 프롬프트(존재 시)를 전달한다.

아래 5개 점수 축을 세 검수자 결과에서 모두 확인한다.

- 정의와 허용값의 일치
- 규칙 문장의 명료성 및 경계 사례 결정성
- 우선순위, 충돌, 다음 규칙 이동
- 프롬프트 본문 전달 및 블라인드 경로 누출 방지
- 근거·범위와 검증 재현성

어느 한 점수라도 90 미만이면 `findings`의 구체적 이유를 definitions 또는 profile에 반영한 뒤 세 검수를 다시 실행한다. 합의되지 않은 해석을 평균으로 덮지 않는다. 세 검수자 모두 모든 축에서 90 이상일 때만 문서·프롬프트 구조 검수를 통과시킨다.

## 프롬프트와 행동 검증

1. `python3 .claude/os/engine/scripts/gt_review.py policy prompt --task <id> --field <field>`로 렌더 결과를 확인한다.
2. 운영 목적지가 설정돼 있으면 먼저 `policy sync-prompt` 미리 보기의 해시·본문을 검토하고, 사용자가 요청한 정책을 적용할 때만 `--yes`로 동기화한다.
3. 규칙마다 참/거짓 증거, 동시 증거, 모호한 증거, 증거 없음 및 다음 규칙 이동 사례를 실행 가능한 테스트로 고정한다.
4. 관찰 사실 수집용 블라인드 프롬프트에는 결론 규칙·정답 값을 보내지 않는지 검증한다.
5. 실제 정확도는 고정된 상품/이미지 표본과 사람이 확인한 GT가 있을 때만 보고한다. 에이전트 구조 점수를 실제 정확도 점수로 표현하지 않는다.

정책 파일을 작성한 것만으로 실제 정확도를 보증하지 않는다. GT 없이 가능한 것은 문장·우선순위·프롬프트 구조의 완성도 검수다.
