# 미션 제출

NextStep 미션의 **제출 실행 절차**를 담당한다.
계정 문제의 원인·해결과 fork PR 규칙 자체는 `github-flow` 스킬에 있다. 이 스킬은 그것을 **자동 점검으로 바꾼 것**이다.
계정 오류가 실제로 발생하면 `github-flow`의 규칙 1·2를 따른다.

## 1. 사전 점검 (항상 먼저)

```bash
.claude/skills/mission-submit/scripts/preflight.sh
```

한 번에 6가지를 검사한다.

| # | 검사 | 잡아내는 문제 |
|---|---|---|
| 1 | origin이 fork인가, 부모는 어디인가 | 잘못된 저장소에서 제출 |
| 2 | gh 활성 계정 · git 자격증명 = fork 소유자인가 | 403, `must be a collaborator` |
| 3 | 부모 레포에 내 ID 브랜치가 있는가 | base 브랜치 부재 |
| 4 | base 대비 제출할 커밋이 있는가 | 빈 PR |
| 5 | 커밋 안 된 변경이 남았는가 | 제출 누락 |
| 6 | 이미 열린 PR이 있는가 | 중복 PR 생성 |

`[FAIL]`이면 **거기서 멈추고 사용자에게 알린다.** 우회하지 않는다.
`[WARN]`은 대부분 계정 문제다. `github-flow` 규칙 2대로 명령 단위 토큰을 먼저 쓴다.

점검값은 모두 origin 원격에서 유도한다. 저장소 이름이나 계정을 하드코딩하지 않으므로 다른 fork 과제에도 그대로 쓴다.

## 2. 커밋

커밋이 필요하면 `ai-coauthor-guard` 규칙에 따라 co-author 트레일러를 포함한다.
이미 커밋돼 있으면 건너뛴다.

## 3. fork에 push

```bash
git push -u origin "$(git rev-parse --abbrev-ref HEAD)"
```

## 4. PR 생성 또는 갱신

**점검 6번에서 열린 PR이 나왔다면 새로 만들지 않는다.** 3번의 push만으로 그 PR에 반영된다.

새로 열 때의 base/head 규칙과 명령은 `github-flow` 규칙 3을 따른다.

## PR 본문

리뷰어가 무엇을 봐야 하는지 알 수 있게 쓴다. 변경 목록만 나열하지 않는다.

```markdown
## 작업 내용
- (무엇을 왜 했는지)

## 리뷰 포인트
- (판단이 갈릴 수 있는 지점, 확신이 없는 선택)
```

## 제출 후

PR 번호와 URL을 사용자에게 알린다. 리뷰 피드백을 받으면 같은 브랜치에 커밋하고 push하면 PR이 갱신된다.
머지된 다음에 새 단계 브랜치를 만든다.
